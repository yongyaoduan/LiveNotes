## 首轮扬声器 → 麦克风对照

在 macOS 26.6.2、Apple Silicon 上，通过扬声器播放同一段英语合成语音，由 LiveNotes 的实际麦克风录音链路收音。音源长 **35.910 秒**，录音包含播放前后的空白，实际约 **42–43 秒**。这次验证使用了物理声学路径；音频文件直送识别器属于另一种测试。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 实际录音长度 | 42.261 秒 | 43.051 秒 |
| 最终转写词数 | 92 | 92 |
| 相对原始口播稿的词错误率 | 0/92，0% | 0/92，0% |
| 保存的转写段数 | 11 | 9 |
| 保存译文非空的段数 | 11/11 | 9/9 |
| 导出音频与对应原录音逐字节一致 | 是 | 是 |
| 保存的英文和译文均出现在 Markdown | 是 | 是 |
| 点击结束至保存完成 | 未单独计时 | 1.7725 秒 |
| 点击导出至导出稿可读取 | 未单独计时 | 0.3731 秒 |

词错误率按英文小写词序计算，忽略标点，以单词插入、删除、替换的最小编辑距离除以参考词数。两版最终词序都与原始 92 词口播稿完全相同，没有多词、少词或额外重复；段数差异来自句子合并与标点切分。上述时间包含 UI 点击和状态检测开销，并非纯识别或磁盘操作耗时。缺少修改前的对应分项计时，因此不能据此计算提速倍数。

这条清晰、短时的音频没有复现修改前最终稿丢句。修改前结束录音会对整个文件重新转写，再处理缺失翻译；修改后的结果直接来自实时识别及结束时的尾句，不经过第二遍整文件识别。因此，两版最终稿都正确，不能证明两版实时字幕同样可靠，也不能据此宣称识别模型准确率提升。

## 首轮实时内容保留

修改后的声学测试保存了 **36 次、约每秒一次**的实时稿采样，其中 25 次已有确认文本。这 25 次非空采样的英文词序均保留上一次完整前缀，没有观察到已保存词语回退或消失。

结束前的实时稿包含 **84 词**；最终稿完整保留这 84 词，再加入尾句 `This is the end of the recording test.`，共 92 词。三个主题短语 `privacy preserving meeting notes`、`reliable translation`、`red, green, and blue` 在结束前及最终稿中均存在。

采样针对已经写入会话文件的确认文本，并非每次屏幕刷新，也不包含完整的临时字幕版本。第一条非空文件采样出现在播放开始约 11.3 秒后；这不能作为屏幕首次字幕延迟。此次声学证据没有可用的逐次实时译文快照，因此不对“所有屏幕上出现过的译文都与保存稿完全一致”作实测结论。

## 已确认的丢句原因

修改前的独立源码副本基于 `fe32556`。三个定向回归测试均失败：较短的最终修正被忽略、提交一个片段时相邻重叠片段被删掉、两个不同短句因显示时间都落在同一秒而只剩一个。修复后不再按字数多少或整数显示时间决定替换，而是按识别结果的来源范围和稳定标识处理。

实测还捕获到苹果临时结果中的 `secondnd`、`Exort`，苹果随后已修正成 `second`、`Export`，但旧的较宽时间范围草稿可能再次写回。修复会保留最终确认结果并清理对应旧草稿。原始 144 条识别事件已经纳入回归数据，回放后恰好得到苹果确认的 9 段最终文本。另有测试覆盖不足一秒的前缀和后缀排序，以及属性区段拆开一个单词时不得拼出残缺单词。

## 连续原生识别

把同一段音源连续重复三遍，以播放速度送入生产音频转换器、原生识别器、结果解析器和转写合并器。输入 **107.729 秒、276 词**，收到 **433 条原生结果、27 条最终结果**。生产合并后的 27 段文本与苹果最终文本完全相同；九组关键句均恰好出现三次，没有应用额外增加、删除或重复的词。

与口播参考稿严格按词比较，有 8 处数字书写替换：`first` → `1st`、`second` → `2nd`、`three` → `3`。仅把这几种明确的数字写法视为等价后，词序完全一致。临时结果中仍出现 `secondnd`、`thirdr`、`thirdrd`、`Exort`，最终保存快照中均为零。此测试不经过麦克风、应用 UI 或翻译，也不是长会议准确率测试。

最终代码另行回放了 144 条短音源结果、433 条连续音源结果和 143 条真实麦克风录音结果。三组快照分别与原生最终的 9、27、11 段逐段完全一致；这些回归检查验证应用组装行为，不掩盖苹果最终结果中的识别错误。

## 大文件导出

调用生产导出函数，导出 **128 MiB 合成文件和 2,000 行现成中英文本**：首次 27.01 毫秒、覆盖已有导出 28.71 毫秒。两次导出的音频字节摘要相同，2,000 行原文和译文全部保留，源文件和会话库未变。

每种操作仅测一次，源和目标位于同一本地文件系统，结果可能受缓存和文件系统复制优化影响。合成文件不可解码；这只验证导出文件复制和文本保留，不代表 128 MiB 真实会议的识别、翻译性能，也不代表跨磁盘的复制速度。

## 声学测试发现的残留问题

后续一次声学运行在实时稿中保留了全部 92 词、10 段和最后一句，但苹果把 `notes` 识别成 `nodes`。相对参考词序有 1 处替换，即 1/92（约 1.09%），没有词语插入或删除。这次精确短语断言在保存前中断，不能算作保存或导出通过。后续存储验证把该主题锚点设为 `privacy preserving meeting`，完整稿件仍单独按 92 词原文比较，识别差异不被隐藏。

随后的存储测试虽然完成了保存和导出，但全文比对发现 104 词，额外保留了旧临时句 `Every sp cons sentence should remain visible when the next sentence begins.`。对应正确句已经存在，不能把这次主题锚点通过当作转写验收通过。修复后的匹配允许同一来源范围中局部的一词、两词修订，并要求前后有足够的共同词；它不会把纯粹增加的后缀当成错误草稿删除。真实录音的 143 条原生结果已加入回归数据，回放后恰好得到 11 条、92 词的原生最终文本，旧句不再残留。

## 权限复用审查

麦克风和语音识别的授权器都会先读取 macOS 当前状态：已经授权则直接返回，尚未决定才请求系统授权，被拒绝或受限制则提示用户处理。启动实时识别及恢复识别时的额外检查也有相同的已授权分支。源码没有重置 TCC 或主动撤销系统权限的操作；同一应用正常重启不会主动清除授权。

8 项权限专项测试全部通过，覆盖尚未决定时申请、申请失败、已经授权及已经拒绝。针对已授权状态，同一个授权器重复调用，以及重新创建授权器后再次调用，麦克风和语音权限的申请次数均为零。这是应用逻辑验证，不代表 macOS 会将不同 ad-hoc 构建认作同一个应用。

应用内的录音提醒此前每次都会出现。1.0.0 在用户首次确认并点击开始时保存偏好；后续点击新录音直接启动，退出重开也复用该偏好。取消首次确认或取消开始不会记为已完成。测试会话使用独立偏好域，避免改写用户的真实设置。

旧 Homebrew cask 的普通卸载步骤包含删除 `app.livenotes.mac.plist`，升级执行旧版本卸载时可能丢失偏好。新的 cask 保留偏好，只有显式使用 `--zap` 才删除。由旧 cask 升级的首次安装仍需保留旧偏好，后续新 cask 升级不再删除它。

已安装的 0.1.3 和此次预览包均为 ad-hoc 签名，没有 Developer ID 身份，bundle ID 则保持 `app.livenotes.mac`。两份应用的 designated requirement 使用不同代码摘要；新包不满足旧包的要求。这意味着即便 bundle ID 和安装路径不变，更新后也可能不能复用系统授权。Apple 在 [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) 中说明，隐私权限复用取决于代码签名身份和 designated requirement，而 ad-hoc 签名不提供跨构建的稳定身份。

因此，本版修复应用确认和偏好保留，但不承诺预览版跨版本系统授权只需一次。正式解决需要持续使用同一团队的 Developer ID Application 身份发布，参见 Apple 的[发行签名说明](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)。从旧 ad-hoc 版首次迁移到正式签名也可能需要再次授权；应用不能覆盖用户手动撤销或系统策略变更。

## 翻译与适用范围

译文全部导出，不代表翻译质量合格。声学对照中的苹果原生翻译把本语境中的 `saving our work` 译为“拯救我们的工作”，把 `existing transcript` 译为“现有成绩单”。这些词义错误仍然存在，此次结果不能当作翻译准确率通过。

这些测试使用单人、清晰英语合成语音，尚不覆盖长会议、多人抢话、口音、背景噪声或中英混说。约每秒的确认稿采样也不能排除两次采样之间的短暂显示问题。保存和导出的速度仍会受音频长度及目标磁盘影响。

测试输入为：

> Today we are testing a local meeting recorder. The first topic is privacy preserving meeting notes. Every spoken sentence should remain visible when the next sentence begins. The second topic is reliable translation. A correction may change a word, but it must preserve the rest of the conversation. The third topic is saving our work. Export should copy the recording and the existing transcript immediately. We do not need to translate the whole meeting again. Finally, remember the three colors: red, green, and blue. This is the end of the recording test.
